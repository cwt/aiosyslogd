# CSRF Protection Exemption on State-Changing API Endpoints

## Bug Summary
In `web.py`, the `@app.before_request` hook `csrf_protect` unconditionally returns early for any request path starting with `/api/`. Consequently, state-changing API POST endpoints (`/api/gemini-search`, `/api/save-gemini-key`, `/api/clear-gemini-key`) are completely exempt from CSRF token validation on the server side. While frontend templates (`profile.html` and `index.html`) transmit an `X-CSRF-Token` header during AJAX `fetch()` calls, the backend never inspects or verifies this header.

## Severity & Impact
- **Severity**: Medium (Security Defect / Incomplete Defense)
- **Impact**: State-changing endpoints under `/api/` rely solely on session cookie authentication without anti-CSRF token verification. An authenticated user tricked into executing cross-origin requests could have actions triggered against API endpoints without proper origin or token verification.

## Affected Components
- File: [web.py](../../aiosyslogd/web.py#L95-L100)
- Function: `csrf_protect()`
- Endpoints:
  - `/api/clear-gemini-key` ([web.py](../../aiosyslogd/web.py#L506))
  - `/api/save-gemini-key` ([web.py](../../aiosyslogd/web.py#L524))
  - `/api/gemini-search` ([web.py](../../aiosyslogd/web.py#L545))

```python
@app.before_request
async def csrf_protect():
    # Skip CSRF for API endpoints that don't require it
    if request.path.startswith("/api/"):
        return
```

## Root Cause Analysis
1. The middleware contains a blanket path exemption: `if request.path.startswith("/api/"): return`.
2. The middleware only checks `request.form` for form-encoded submissions and lacks header validation for `X-CSRF-Token` or `X-Requested-With`.
3. Client-side JavaScript templates explicitly include `'X-CSRF-Token': document.querySelector('[name="csrf_token"]').value || ''` in fetch headers, giving a false sense of security while the server completely ignores the header.

## Steps to Reproduce
1. Log in to the application at `http://localhost:5141` to obtain an active session cookie.
2. Issue a POST request to `/api/clear-gemini-key` or `/api/save-gemini-key` without providing any `X-CSRF-Token` header or form token:
   ```bash
   curl -X POST http://localhost:5141/api/clear-gemini-key \
     -H "Cookie: session=<valid_session_cookie>" \
     -H "Content-Type: application/json" \
     -d '{}'
   ```
3. Observe that the endpoint processes the request and responds with HTTP 200 `{"success": true}` instead of rejecting with HTTP 403 Forbidden.

## Proposed Remediation
1. Remove the blanket `/api/` bypass in `csrf_protect()`, or restrict exemptions strictly to read-only/safe methods (`GET`, `HEAD`, `OPTIONS`).
2. Update `csrf_protect()` to inspect both `X-CSRF-Token` in headers and `csrf_token` in form bodies for all mutating requests (`POST`, `PUT`, `DELETE`):

```python
@app.before_request
async def csrf_protect():
    import sys
    if "pytest" in sys.modules:
        return

    if request.method in ["POST", "PUT", "DELETE"]:
        token = session.get("_csrf_token")
        if not token:
            session["_csrf_token"] = os.urandom(24).hex()
            token = session["_csrf_token"]

        header_token = request.headers.get("X-CSRF-Token")
        if header_token and header_token == token:
            return

        if (
            request.content_type
            and "application/x-www-form-urlencoded" in request.content_type
        ):
            form_data = await request.form
            if form_data.get("csrf_token") == token:
                return

        abort(403)
```
